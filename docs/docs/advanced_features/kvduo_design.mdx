## 概述

KVDuo 面向非 P/D 分离的稀疏注意力推理。完整 KV 页（FULL）和稀疏热点条目（HOT）共用 HBM 物理页池，Host 保存有效后备。Decode 空间不足时，先回收合格 FULL 页，再按近期访问收益调整 HOT 容量；等待的 prefill 只可在预算内借用低收益的 HOT 追加容量，不回收活跃 FULL。

## 容量与统计口径

- 一个 HOT 对象对应 `(request, layer)`，同一请求的各层独立管理。
- 一张物理页包含所有存储层的同号页片段。用作 FULL 时，各层保存同一序列区间；用作 HOT 时，全部片段保存同一逻辑层的稀疏条目。片段可以由 stride 分隔，无需相邻。
- 一张 HOT 页的条目数记为 K，等于存储层数乘以每层页条目数；存储层数不一定等于逻辑层数。例如 21 个存储层、每层 64 个条目，则 K 为 1344。
- HOT 按需建立，初始页数为 `ceil(top_k / K)`，最多 8 页；最低页数不能超过 8。
- 基础页是最近一次安全 hand 处理保留的物理页；此后扩容追加的是增量页。基础页身份固定，内容正常参与 LRU 替换。

只统计实际执行且解析成功的 decode。FULL/tail 直接命中、已有 HOT 命中和 Host miss 互斥；本轮 H2D 新换入不算命中。零命中步骤正常观察，padding、无效访问、Graph 捕获、预热及搬运不计入。

两类收益统计均使用 EMA：首次观察直接初始化，此后旧值占 63/64、本步值占 1/64。超过 64 个有效观察步才可评估，观察不足不能视为零损失。

## 设计点 1：FULL 与 HOT 混合驻留

### 访问与回收

Prefill 生成 FULL KV，支持前缀复用。Decode 依次查找 FULL/tail、对应对象的 HOT；均未命中时，从 Host 换入 HOT，优先用空槽，否则按条目 LRU 替换。

活跃 FULL 仅因 decode 必需分配或 HOT 扩容回收，包括已完成 prefill、尚未首次 decode 的请求。FULL 只能在 Host 副本完整、有效且版本同步后回收。候选页排除共享引用保护、最新 tail、未写满页，以及使用、分配或传输中的页。仅单个活跃请求持有的 Radix 独占后缀可先从树中摘出，将槽位所有权交还请求，再参与 FULL 回收；共享节点和无法安全转移的前缀继续保护。摘出不搬运或释放 KV，后续前缀匹配不会将该后缀误报为 GPU 命中，有效 Host 副本仍可用于恢复。Tail 默认保护最新 2 页。

设置 `full_reclaim_policy="request"` 可按请求批量回收：优先选择合格 FULL 页数减去尚需新增最低 HOT 页数后净收益最大的请求，同分优先最早进入 decode 的请求，再按请求槽位排序。一次释放选中请求的全部合格页，净空间够用即停止；GPU 汇总和选择，不按页访问时间排序。

默认使用 `full_reclaim_policy="page"` 逐页策略：跨活跃请求按 FULL 页内最近条目访问时间排序，最久未访问的页优先；同分按请求槽位、页偏移排序，空间够用即停止。两种策略均保留上述保护，只清除 GPU 完整映射，被驱逐页中的热点不主动搬入 HOT。

在 `"page"` 模式下，decode 必需分配或 HOT 扩容优先按请求自身的 FULL 页 LRU 回收，每个请求以其新增页和最低 HOT 容量缺口为目标；扣除首次混合驻留所需的最低 HOT 页后仍有缺口，再使用全局页 LRU。批次中无分配需求的请求不进入优先回收阶段。

该配置控制 decode 的常规 FULL 压力回收，不用于 prefill 准入。

### 空间分配

| 需求 | 空间不足时的处理 |
| --- | --- |
| Decode 必需分配 | 先回收合格 FULL，再尝试普通 HOT 缩容 |
| 可选 HOT 扩容 | 保护 prefill 和最低 HOT 额度后，先使用空闲页，再回收合格 FULL，最后尝试普通 HOT 缩容 |
| Prefill | 使用空闲页及无人使用的可驱逐 Radix 缓存；剩余缺口仅交给设计点 3 的 HOT 回退 |

共享池之外的 logical、SWA、indexer、压缩状态及 Host 预算仍需检查。请求进入混合驻留时，首次需要 HOT 的 decode 前必须补足最低容量。

KVDuo 的 SWA 只为活跃计算保留数据，不为未来前缀复用长期占用 HBM。每个 prefill chunk 完成后增量备份 Host SWA，并安全释放窗口外请求自有 SWA，避免长 prompt 占满独立池而无法继续。完成 prefill、进入 decode 时同样清理请求头部的过期 SWA，后续 decode 准入前继续清理。共享前缀的 SWA 窗口由各请求独立加锁，仍被其他请求或待执行、在途 prefill 使用的数据保持保护。清理按页对齐，保留当前窗口、必要保护区及未完成计算所需的数据。

请求结束后释放无人使用的 HBM SWA，保留有效的 Host 前缀副本。DeepSeek-V4 在完成 prefill chunk、清理 SWA 前，备份完整页的 C4、indexer、C128 历史，以及 SWA 和相关 C4 压缩状态；decode 结束前也保存最后一个可用边界，复用已有主 KV Host 后备。Host 历史池与窗口池容量有上限，窗口池按 `host_to_device_ratio` 配置，淘汰未被请求或搬运引用的旧记录；因此会增加 Host 内存和备份开销。Host SWA 和相关状态保留各有效页对齐前缀边界，后续 chunk 复用已有备份，只搬运缺失记录。Host 容量不足时仍按缓存规则淘汰，不能无限保留。备份及有效性元数据异步传回 Host，完成事件确认后才发布，源页释放按 GPU 事件排序。

前缀复用只选择各 TP rank 都具备完整、有效副本的页对齐边界：恢复缺失的历史数据及边界前的 SWA 窗口和压缩状态，然后继续 prefill。只分配恢复窗口所需的 HBM SWA，不恢复整段历史 SWA。C128 请求状态按 HiCache 的页对齐规则重新开始。副本缺失、过期或尚未完成搬运时缩短命中；没有有效边界才从头计算。取消、请求结束和槽位复用释放相关引用，缓存清空同时清理 Host 副本。纯 HiSparse 路径保持原行为。

`decode_emergency_reclaim` 默认关闭，可设置 `decode_emergency_reclaim=true` 开启。它仅用于必需 decode：正常 FULL 回收和预算内 HOT merge 后仍缺页时，将可安全处理、未锁定的 HOT 对象缩至最低容量，优先处理可释放页数最多的对象，空间足够即停止。它允许观察不足或超出普通 miss 预算的对象应急缩容，优先保留运行中的请求，可能增加 H2D 换入和 merge 停顿；最低容量、页保护、TP 一致性和 prefill 预留仍有效。prefill 和可选扩容不使用此路径。

首次 decode 准入失败时，日志记录逻辑／SWA、Host、物理空闲页、HOT 最低额度、prefill 预留及回收结果；整请求回退仍作为兜底。应急 HOT 回收无法解决独立池不足。

回退前检查并预留完整 prompt 所需的主 KV Host 后备。已完成 chunk 的备份和 staging 分配将预留转为真实占用；取消或请求结束时释放剩余预留及其前缀 pin。

## 设计点 2：按近期收益调整 HOT 容量

### 扩容与收益估计

新的 top-k H2D 换入需要替换已占用槽位时，提出增加一张 HOT 页的申请；同一安全边界前的多个事件合并一次。达到 8 页或空间不足时，在当前容量内继续 LRU 换入，不积累延期申请。

没有真实扩容申请，或空闲页尚不能覆盖 prefill 保护量时，不通过可选扩容路径执行普通 merge 为 prefill 腾空间。

`lru_slots` 从 LRU 到 MRU 保存替换顺序。统计按更新前的排名，从 MRU 端每 K 个槽位划一段，记录最多 8 段的 HOT Hit EMA、一个 Miss EMA 和观察步数；FULL/tail 命中不计入分段。

统计成熟后，选择满足最低容量的最小保留页数，使被截掉段的 Hit EMA 总和不超过 Miss EMA 的 `max_relative_miss_increase` 倍，默认 10%。Miss 为零时，只能截掉贡献为零的段；未成熟时保持容量。

例如 4 页的分段命中为 `[100, 30, 5, 1]`，Miss EMA 为 100，预算为 10：保留 2 页会截掉 6 次预计命中，保留 1 页会截掉 36 次，因此目标为 2 页。

扩容保留全部已有 EMA 和观察步数，新增尾段继承扩容前最后一个已有段的 Hit EMA。该初值是先验，不代表真实命中，也不会使只有 20 步观察的对象立即成熟。

### Hand 扫描与 merge

共享池的 hand 按请求槽位优先、层号递增循环扫描，处理或跳过后推进，跨调用保留位置。跳过不活跃、未建立 HOT、staging、generation 不符、受使用或搬运保护，以及被 prefill 锁定的对象。

每个安全处理对象按上述预算确定目标。容量不变也建立基础页记录、更新处理序号，并重置设计点 3 统计；设计点 2 统计保留。未经安全处理的对象没有基础记录。

实际缩容时：

1. 按真实 LRU 保留 MRU 端目标容量内的有效条目，不足时全部保留。
2. 保留包含最多存活条目的目标数量物理页，同分优先原页列表中靠前的页。
3. 将释放页中的存活 KV 搬入保留页的空槽或被丢弃条目槽位。
4. 发布映射和容量，保持存活条目的相对 LRU 顺序，空槽优先；建立新基础记录并清零两类统计。
5. 等待搬运和元数据更新完成，再归还物理页。

同边界中被实际缩容对象的扩容申请会取消。空间够用即停止，超额释放页进入空闲池；完整一轮无释放、无外部状态变化时停止，不放宽预算。请求结束不重置全局 hand。

### GPU 规划

CUDA 路径中，CPU 筛选可安全处理的对象并验证 generation、页所有权和 TP 一致性；GPU 根据 EMA 计算缩容目标，按 hand 顺序筛选覆盖缺口的处理前缀。CPU 仅读取该前缀的紧凑规划，不下载完整 EMA。

普通 merge 仍逐对象执行。GPU 用一个 CTA 规划存活条目、保留页、搬运向量和暂存元数据。容量相关工作区放在全局 scratch，避免共享内存随最大槽位数增长。

确定缩容目标后，GPU 在同一 stream 中顺序规划、复制 KV（含必要 scale）、发布元数据并清零统计，复用固定工作区。CPU 在归还页前只读取一次状态、搬运数和保留页位掩码三个 int32 完成摘要，不读取完整条目数组。完整页直接按已知页编号归还，避免再次筛选和去重；规划失败不搬运或发布。原张量地址、形状和 stride 保持固定，完成等待和 KV 搬运仍有开销。

## 设计点 3：对象级 Prefill 回退与恢复

### 准入方案

沿用原调度器的请求顺序、组批和分块。新 prefill 必须能覆盖剩余完整输入、Host 前缀恢复及确需继续生成时首次 decode 新增的 FULL 页；分块期间保留未使用额度，避免已开始的长请求因缺页卡住。空间检查计入其他预留和已有混合对象的 HOT 最低额度。只回收无人使用的 Radix 缓存，剩余物理缺口由合格 HOT 回退提供；预计但未安全完成的释放不算空闲。单个请求的完整 FULL 容量超过物理池时拒绝该请求。

快速回退候选必须活跃、非 staging、未锁定，具有有效基础记录和增量页，增量观察超过 64 步，且可安全释放。基础页须为当前页列表的前缀并满足最低容量，generation、所有权和快照须一致。

每个对象的增量页 Hit EMA 不得超过当前增量评估阶段 Miss EMA 的默认 10%；Miss 为零时，仅允许增量命中也为零。对象独立判断，不借其他层额度；没有增量页或尚未建立 HOT 的层不提供空间，也不随同请求其他层锁定。

按 hand 最近处理序号从新到旧选择，同分按请求槽位、层号排序。每个对象释放全部增量页，直到足够覆盖缺口；不按代价排序或按剩余缺口裁剪释放范围。

### 固定累计预算

首次成功回退前，冻结当前具有有效成熟增量统计的活跃对象的 Miss EMA 总量，作为本轮参考。仍锁定对象在回退时预留的代价，加上新方案的增量命中代价，不得超过该参考的默认 10%。

预留代价不随 EMA 衰减减少，直到对象恢复弹性或请求结束才移除。新请求不扩大本轮参考，没有有效参考的对象不能加入；参考失效或请求结束时移除其贡献。预算因此不足时，不撤销已完成回退，但不再增加代价；全部锁定解除后结束本轮。

引用按对象、请求 generation 和基础评估阶段绑定。两类评估的 miss 原始计数相同，但观察阶段和重置规则不同，因此分别维护 EMA。

### 无搬运回退与锁定

空间、对象代价、累计预算及其他内存池条件全部满足后，才建立 prefill 预留和对象锁定，并绑定关联 prefill。没有完整方案则继续等待，不先部分回收。

回退保留基础页的当前 KV，丢弃增量页条目，不搬运 KV。批量 GPU 元数据更新稳定过滤掉基础容量外的 LRU 槽位，保持基础槽位编号、存活条目相对顺序和空槽优先，清空容量外元数据后统一安全释放。

锁定对象固定在基础容量，正常 decode、H2D 和 LRU，但不参与可选扩容或普通 merge，不累积延期扩容事件。同请求其他对象继续独立管理。回退清零两类统计，保留累计预算中的代价。

准入取消时撤销对应预留、锁定及代价，已丢弃的 KV 不主动恢复。执行失败不得继续准入，也不得交出尚未安全释放的页。

### Decode 分配与 FULL 回收

Prefill 完成不会主动将请求转为混合驻留，但其他请求的 decode 必需分配或 HOT 扩容可以回收其合格 FULL，无需等待它首次 decode。新混合请求各层的最低 HOT 容量必须先补齐，释放量扣除这部分成本后才可用于扩容。

首次 decode 的准入检查临时使用自己的预留额度，实际分配成功后才兑现，普通与混合 prefill/decode 路径一致；检查或分配失败保留额度，请求结束或取消时清理。剩余输出只需 prefill 产生的一个 token 时，不额外预留 decode 页。这是分配额度，不是对已有 FULL 页的驻留保证。

新 prefill 及 Host 前缀恢复不能抢占活跃 FULL。空间不足时 prefill 等待，让 decode 继续推进；decode 回收或请求结束腾出空间后，再尝试准入。

### 完成后解锁

关联 prefill 全部完成或取消、对象可安全处理且各 TP rank 一致后，在安全边界解除锁定和预算代价，无需等待额外空闲页。同请求各层独立管理，尚在使用或搬运中的对象继续保护。

解锁保持当前容量和统计，不立即扩容，也不补执行锁定期间的旧事件。之后新的容量不足事件才可触发扩容，上限恢复为 8 页。

可选扩容仍保护已准入 prefill 的剩余 FULL 额度、已有混合对象的最低 HOT 容量，以及下一执行计划的未覆盖必需空间。没有真实扩容申请，或空闲页尚不足以覆盖保护量时，不回收 FULL 或普通 HOT 来填补 prefill 的缺口；该缺口由 prefill 准入处理。

## 生命周期与执行约束

| 事件 | 设计点 2 统计 | 设计点 3 统计与状态 |
| --- | --- | --- |
| 首次建立 HOT | 从零观察 | 尚无基础记录，初始弹性 |
| 安全扫描，容量不变 | 保留 | 重建基础并清零增量评估 |
| 实际普通缩容 | 清零 | 重建基础并清零增量评估 |
| 首次从基础扩容 | 保留，新增尾段继承旧尾段 EMA | 重启增量评估，保留基础页身份 |
| 后续扩容 | 保留，新增尾段继承旧尾段 EMA | 保留 |
| Prefill 回退 | 清零 | 清零评估，锁定并保留预算代价 |
| 仅解除锁定 | 保留 | 保留统计，移除预算代价 |
| 请求结束或槽位复用 | 清空 | 清空基础、限制、预留、关联和预算引用 |

物理扩缩容在 decode 步之间执行，先准备资源，再修改状态。旧访问、在途传输、KV 搬运和元数据发布完成后才归还页；TP 各 rank 的准入、释放和恢复方案必须一致。

CUDA Graph 的元数据地址、形状和 stride 固定，token/location padding 与 LRU 宽度分别处理。大容量 resolver 在初始化时检查设备资源，选择共享或持久化全局 scratch。

请求结束先完成尾部写回和在途操作，再按前缀缓存规则处理完整 KV，释放 HOT 及其他请求独占资源。前缀复用只接受从序列起点开始、所有所需存储层均完整有效的连续 FULL 页；共享页仅在最后一个保护引用消失后释放。

容量收益统计和增量评估统计合计 60 bytes／对象，不含对齐、临时工作区及控制记录。全部请求绑定状态验证 generation。

## 限制与评估

分段命中和增量页命中都是近期收益估计，不模拟缩容后的缓存演化。扩容尾段先验、访问变化及 EMA 滞后可能导致误判；预算不保证实际 miss、TTFT、TPOT 或 SLO 的严格上界。Decode FULL 回收引入的换入代价不包含在 HOT 回退预算中。

评测关注实际 miss、净释放量、prefill 等待、吞吐和尾延迟，以及对象锁定时长、重复回退、解锁后扩容行为、Host 备份和 GPU merge 的规划／搬运／同步成本。

## 启动与配置

在 NVIDIA CUDA 环境中，将 `MODEL_PATH` 替换为受支持的稀疏注意力模型：

```bash
python3 -m sglang.launch_server \
    --model-path MODEL_PATH \
    --tp-size 8 \
    --enable-kvduo \
    --kvduo-config='{"top_k": 2048, "host_to_device_ratio": 2, "swap_in_block_size": 960, "tail_protected_pages": 2}'
```

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `top_k` | `2048` | 每层选择宽度；最低 HOT 页数为 `ceil(top_k / K)` |
| `host_to_device_ratio` | `2` | Host pool 相对 device pool 的容量比例 |
| `swap_in_block_size` | `960` | Resolver CUDA block 线程数，须为 32 的倍数且不超过设备上限，通常为 32–1024 |
| `tail_protected_pages` | `2` | 每请求保护的最新 FULL 页数 |
| `full_reclaim_policy` | `"page"` | `"request"` 按请求批量释放全部合格 FULL 页；`"page"` 按页 LRU 回收 |
| `max_relative_miss_increase` | `0.10` | 普通缩容、对象回退及累计预算共用的预计 miss 相对增幅容忍比例 |
| `decode_emergency_reclaim` | `false` | 开启后，必需 decode 的普通回收失败时允许 HOT 应急缩至最低容量，优先避免整请求回退 |

前四项须为正整数，回收策略只接受 `"request"` 或 `"page"`，miss 容忍比例须为有限非负数，应急开关须为布尔值；未知字段报错。`--kvduo-config` 必须配合 `--enable-kvduo`。默认 10% 是实验初值。

KVDuo 要求 RadixTree，不能与 HiSparse、HiCache 或 speculative decoding 同时启用；支持 chunked prefill，不改其分块设置。通用 DSA 和 DeepSeek-V4 均按实际存储层数计算 HOT 页容量；`flashmla_kv` 要求 FP8 KV 存储，BF16 使用受支持的其他稀疏 backend。
