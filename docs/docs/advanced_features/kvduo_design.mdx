## 概述

KVDuo 面向非 P/D 分离的稀疏注意力推理。完整 KV 页（FULL）和稀疏热点条目（HOT）共用 HBM 物理页池，Host 保存有效后备。Decode 空间不足时，先回收合格 FULL 页，再按近期访问收益调整 HOT 容量；Prefill 在 indexer/C128 的 80% 历史容量预算内准入，可回收合格活跃 FULL，但不缩减 HOT。

## 容量与统计口径

- 一个 HOT 对象对应 `(request, layer)`，同一请求的各层独立管理。
- 一张物理页包含所有存储层的同号页片段。用作 FULL 时，各层保存同一序列区间；用作 HOT 时，全部片段保存同一逻辑层的稀疏条目。片段可以由 stride 分隔，无需相邻。
- 一张 HOT 页的条目数记为 K，等于存储层数乘以每层页条目数；存储层数不一定等于逻辑层数。例如 21 个存储层、每层 64 个条目，则 K 为 1344。
- HOT 按需建立，最低页数为 `ceil(top_k / K)`；不设 8 页上限，扩容受共享物理池可用空间及必要预留约束。

只统计实际执行且解析成功的 decode。FULL/tail 直接命中、已有 HOT 命中和 Host miss 互斥；本轮 H2D 新换入不算命中。零命中步骤正常观察，padding、无效访问、Graph 捕获、预热及搬运不计入。

每个 HOT 条目使用 2-bit 饱和频次计数 `freq`，范围为 0–3；不再维护 HOT LRU、分段 EMA 或观察步数。

## 设计点 1：FULL 与 HOT 混合驻留

### 访问与回收

请求分为完整驻留模式（`FULL_RESIDENT`）和热点驻留模式（`HOT_RESIDENT`）。首次驱逐 FULL 后进入热点驻留；旧有混合驻留标记继续作为模式状态，不额外复制 Graph 元数据。热点驻留不表示所有 FULL 都已消失，共享及其他受保护页仍可保留。

热点驻留请求在整页写回时登记旧 Tail 清理任务，下一安全边界确认 Host 备份就绪后，批量释放已离开 Tail 范围的完整、版本有效且无保护的旧页，不要求发生空间压力。旧读访问由 stream 顺序保护，映射更新完成后才归还物理页。清理游标从进入热点驻留时的 Tail 起点向前推进；每次仅扫描新增过期页和独立保存的受阻页，不重复扫描已释放区间，也不主动搬入 HOT。Host 尚未就绪、版本或使用保护挡住的页保留重试；已被其他路径释放的页从重试集合移除。释放成功后才发布进度，各 TP rank 的选择和进度保持一致。未就绪备份延后处理，任务绑定 generation，请求结束或槽位复用时清除。

该清理可能增加后续 Host 换入；它复用现有回收的规划和完成同步，并非零开销，但不会每个 decode 步都启动历史扫描。完整驻留请求保持 FULL，未改变私人请求结束 HBM 清理和 Host 前缀复用。

Prefill 生成 FULL KV，支持前缀复用。Decode 依次查找 FULL/tail、对应对象的 HOT；均未命中时，从 Host 换入 HOT，优先用空槽；暂时无法扩容时，按低频优先替换，同频按槽位编号选择，并保护本轮已命中的 HOT 条目。

活跃 FULL 可因 decode 必需分配、HOT 扩容或通过历史预算检查的 Prefill 准入而回收，包括已完成 prefill、尚未首次 decode 的请求。FULL 只能在 Host 副本完整、有效且版本同步后回收。候选页排除共享引用保护、最新 tail、未写满页，以及使用、分配或传输中的页。仅单个活跃请求持有的 Radix 独占后缀可先从树中摘出，将槽位所有权交还请求，再参与 FULL 回收；共享节点和无法安全转移的前缀继续保护。摘出不搬运或释放 KV，后续前缀匹配不会将该后缀误报为 GPU 命中，有效 Host 副本仍可用于恢复。Tail 默认保护最新 2 页。已释放的 FULL 区间按请求 generation 记录，后续回收跳过这些区间；暂受保护或 Host 尚未就绪的页继续保留为候选。

按请求批量回收：优先选择合格 FULL 页数减去尚需新增最低 HOT 页数后净收益最大的请求；净收益相同时优先混合驻留，再按最早进入 decode、请求槽位排序。一次释放选中请求的全部合格页，净空间够用即停止；GPU 汇总和选择，不按页访问时间排序。

回收保留上述保护，只清除 GPU 完整映射，被驱逐页中的热点不主动搬入 HOT。

按请求回收后，先扣除 decode 必需分配、最低 HOT 容量和已有预留，再使用净空闲空间。Prefill 只回收满足安全条件的 FULL，不执行 HOT merge。

### 空间分配

| 需求 | 空间不足时的处理 |
| --- | --- |
| Decode 必需分配 | 先回收合格 FULL，再尝试普通 HOT 缩容 |
| 可选 HOT 扩容 | 保护 prefill 和最低 HOT 额度后，先使用空闲页，再回收合格 FULL，最后尝试普通 HOT 缩容 |
| Prefill | 通过 80% 历史预算检查后，先使用空闲页和闲置 Radix 缓存，再回收合格活跃 FULL；不缩减 HOT |

共享池之外的 logical、SWA、indexer、压缩状态及 Host 预算仍需检查。请求进入混合驻留时，首次需要 HOT 的 decode 前必须补足最低容量。

KVDuo 的 SWA 只为活跃计算保留数据，不为未来前缀复用长期占用 HBM。每个 prefill chunk 完成后增量备份 Host SWA，并安全释放窗口外请求自有 SWA，避免长 prompt 占满独立池而无法继续。完成 prefill、进入 decode 时同样清理请求头部的过期 SWA，后续 decode 准入前继续清理。共享前缀的 SWA 窗口由各请求独立加锁，仍被其他请求或待执行、在途 prefill 使用的数据保持保护。清理按页对齐，保留当前窗口、必要保护区及未完成计算所需的数据。

请求结束后释放无人使用的 HBM SWA，保留有效的 Host 前缀副本。DeepSeek-V4 在完成 prefill chunk、清理 SWA 前，备份完整页的 C4、indexer、C128 历史，以及 SWA 和相关 C4 压缩状态；decode 结束前也保存最后一个可用边界，复用已有主 KV Host 后备。Host 历史池与窗口池容量有上限，全部 Host KV 后备池由 `host_ratio` 统一配置，淘汰未被请求或搬运引用的旧记录；因此会增加 Host 内存和备份开销。Host SWA 和相关状态保留各有效页对齐前缀边界，后续 chunk 复用已有备份，只搬运缺失记录。Host 容量不足时仍按缓存规则淘汰，不能无限保留。备份及有效性元数据异步传回 Host，完成事件确认后才发布，源页释放按 GPU 事件排序。

前缀复用只选择各 TP rank 都具备完整、有效副本的页对齐边界：恢复缺失的历史数据及边界前的 SWA 窗口和压缩状态，然后继续 prefill。只分配恢复窗口所需的 HBM SWA，不恢复整段历史 SWA。C128 请求状态按 HiCache 的页对齐规则重新开始。副本缺失、过期或尚未完成搬运时缩短命中；没有有效边界才从头计算。取消、请求结束和槽位复用释放相关引用，缓存清空同时清理 Host 副本。纯 HiSparse 路径保持原行为。

`decode_emergency_reclaim` 保留为兼容配置，默认关闭。新的频次 Hand 已不受观察门槛或 miss 预算限制，因此该开关不再提供额外的缩容权限。最低容量、使用保护、TP 一致性和预留始终有效。

首次 decode 准入失败时，日志记录逻辑／SWA、Host、物理空闲页、HOT 最低额度、prefill 预留及回收结果；整请求回退仍作为兜底。应急 HOT 回收无法解决独立池不足。

准入前检查并预留完整 prompt 所需的主 KV Host 后备。已完成 chunk 的备份和 staging 分配将预留转为真实占用；取消或请求结束时释放剩余预留及其前缀 pin。

## 设计点 2：Adaptive Hot Buffer Allocation

### 频次与扩容

新换入条目 `freq=0`；实际 HOT 命中时加一，最大为 3。频次更新融合在 resolver 的命中扫描中，不额外启动更新 kernel。FULL/tail 命中、新发生的 H2D、padding、预热和搬运不增加频次。

新的 top-k H2D 换入需要替换已占用槽位时，申请增加一张 HOT 页，同一处理边界前的事件合并一次。扩容保留原条目及频次，新槽为空；没有固定最大页数。先使用空闲页，空间不足时回收合格 FULL，随后尝试 HOT merge。扩容仍须保护必要预留；暂缓的申请不累积，后续由新的容量不足事件触发。

### Hand 与 merge

Hand 按请求进入热点驻留的顺序扫描，请求内逐层处理 HOT 对象。跳过受保护、正在 staging、generation 失效或处于最低容量的对象。扩容申请者也可以参与 merge；若被缩容，取消其本轮扩容申请，后续由新事件触发。

每次 merge：

1. 仅保留操作前 `freq=3` 的有效条目，其余丢弃。
2. 根据存活条目数计算所需整页数，至少保留 `ceil(top_k / K)` 页。
3. 优先留下包含最多存活条目的物理页，将其余存活条目搬入保留页的空槽。
4. 存活条目频次除以 2，即 3 变为 1；不把搬运视作访问。
5. 发布映射和容量，确认旧访问、搬运及更新完成后归还物理页。

一次 merge 可以不释放页，Hand 仍前进。允许跨轮继续扫描：没有 decode 插入时，第一轮保留的 3 已变成 1，下一轮可进一步缩容。所有可处理对象均到最低容量或不可处理时结束，避免无法释放空间的无限循环。

### GPU 执行

每个对象维护 token、location 和打包的 2-bit freq；元数据按需扩展并适度预留，实际 HOT 物理页仍逐页分配。freq 存储独立于 FULL/HOT 物理页池及 indexer/C128 容量预算，不按 logical 上限预分配，也不从物理池扣除；其实际 HBM 占用可以使总分配超过 `mem-fraction-static`，但仍受真实显存容量约束。当前轮命中保护使用临时槽位标记。扩容批量发布指针和容量，预留范围内复用元数据存储。CUDA Graph 读取固定地址的指针表，扩缩容在安全边界替换该对象的存储并发布新指针，无需预分配每对象最大池容量或重新捕获 Graph。

GPU 选择保留页、规划并搬运存活 KV；CPU 接收页选择结果，检查 TP 一致性后完成页所有权与 allocator 更新。resolver 使用按 top-k 大小分配的全局 scratch，不随 HOT 容量增大而申请巨量 shared memory。

## 设计点 3：按历史容量预算准入 Prefill

沿用原调度器的请求顺序和分块大小。新请求准入后，预计 indexer/C128 占用不得超过各自已分配容量的 80%。按页计入当前占用、其他已准入请求尚未分配的历史容量、本请求完整剩余输入及确需继续生成时首次 decode 的新增页，不只计算当前 chunk。默认 logical 目标为普通路径的 2.5 倍时，80% 门槛约对应普通路径目标的 2 倍历史 token 容量，不是总 HBM 使用率。

Host 仍为完整输入预留后备。HBM FULL 页按当前 chunk 和本轮 Host 前缀恢复预留，最后一个 chunk 额外预留首次 decode 所需页。先使用空闲空间和闲置 Radix 缓存；不足时可按请求回收合格的活跃 FULL，包括完成 prefill 但尚未首次 decode 的请求。共享页、Tail、正在使用的页和 Host 副本未就绪的页继续保护。回收后扣除新热点请求各层的最低 HOT 容量、活跃请求下一步 decode 需求及已有预留，再判断本次执行能否放下；Prefill 不触发 HOT merge。

已准入长请求的后续 chunk 使用其历史预留，不因 decode 占用了部分 20% 余量而重新应用新请求门槛；每个 chunk 仍检查实际 logical、SWA、Host 和物理空间。空间不足时保留进度并等待，单请求超过 80% 历史预算或完整 FULL 物理容量时明确拒绝。20% 是 decode 余量，不保证任意输出长度都能完成，也不保证连续 prefill 期间的 decode 延迟。

不再维护基础页、增量命中统计、累计回退预算或 HOT 扩容锁定。HOT 扩缩容继续遵循设计点 2。准入失败、取消或请求结束时，清理对应预留和引用。

### Decode 分配与 FULL 回收

Prefill 完成不会主动将请求转为混合驻留，但其他请求的 decode 必需分配或 HOT 扩容可以回收其合格 FULL，无需等待它首次 decode。新混合请求各层的最低 HOT 容量必须先补齐，释放量扣除这部分成本后才可用于扩容。

首次 decode 的准入检查临时使用自己的预留额度，实际分配成功后才兑现，普通与混合 prefill/decode 路径一致；检查或分配失败保留额度，请求结束或取消时清理。剩余输出只需 prefill 产生的一个 token 时，不额外预留 decode 页。这是分配额度，不是对已有 FULL 页的驻留保证。

新 prefill 及 Host 前缀恢复共同通过上述准入检查。恢复执行只消费已获批的物理预留，不额外触发 FULL 或 HOT 回收；预留不足则取消本次准入。

可选扩容仍保护已准入 chunk 和首次 decode 的预留额度、已有混合对象的最低 HOT 容量，以及通过独立池预算检查后、下一执行计划的未覆盖必需空间。因 Host、logical 或 SWA 不足而被拒绝的候选不建立额外 HBM 保护量。没有真实扩容申请，或空闲页尚不足以覆盖保护量时，不回收 FULL 或普通 HOT 来填补 prefill 的缺口；该缺口由 prefill 准入处理。

## 生命周期与执行约束

首次建立 HOT 时槽位为空、频次为零；扩容保留已有条目频次，merge 保留高频条目并衰减。请求结束或槽位复用清空该请求元数据、Hand 条目、预留和引用，不重置全局 Hand 的扫描进度。

物理扩缩容在 decode 步之间执行，先准备资源，再修改状态。旧访问、在途传输、KV 搬运和元数据发布完成后才归还页；TP 各 rank 的准入和释放方案必须一致。

CUDA Graph 使用的指针表、容量表和 scratch 地址固定。对象存储替换后，旧 tensor 在 GPU 读者和指针发布完成前保持存活。

请求结束先完成尾部写回和在途操作，再按前缀缓存规则处理完整 KV，释放 HOT 及其他请求独占资源。前缀复用只接受从序列起点开始、所有所需存储层均完整有效的连续 FULL 页；共享页仅在最后一个保护引用消失后释放。

频次占每条目 2 bit，不含 token、location、临时工作区和控制记录。全部请求绑定状态验证 generation。

## 限制与评估

频次是近期复用的轻量代理，不模拟缩容后的缓存演化。merge 会丢弃低频条目，可能增加后续 H2D；无释放的扫描也有成本。取消容量上限不意味着无限 HBM，仍须检查物理池、Host 及独立逻辑资源。策略不保证实际 miss、TTFT、TPOT 或 SLO 的严格上界。

评测关注实际 miss、净释放量、prefill 等待、吞吐和尾延迟，以及准入频率、Host 备份和 GPU merge 的规划／搬运／同步成本。

## 启动与配置

在 NVIDIA CUDA 环境中，将 `MODEL_PATH` 替换为受支持的稀疏注意力模型：

```bash
python3 -m sglang.launch_server \
    --model-path MODEL_PATH \
    --tp-size 8 \
    --enable-kvduo \
    --kvduo-config='{"top_k": 2048, "host_ratio": 2.0, "swap_in_block_size": 960, "tail_protected_pages": 2}'
```

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `top_k` | `2048` | 每层选择宽度；最低 HOT 页数为 `ceil(top_k / K)` |
| `host_ratio` | `2.0` | Host 相对设备池的容量倍率，与 HiCache 默认倍率一致；独立于 logical 容量倍率 |
| `logical_capacity_ratio` | `2.5` | 自动 logical 目标相对普通路径物理容量目标的倍数；不会随最终物理池缩小而降低 |
| `logical_capacity_tokens` | `0` | 非零时指定独立的 logical token 总容量，覆盖倍率目标，按页向上对齐；DeepSeek-V4 使用压缩前 token 单位 |
| `swap_in_block_size` | `960` | Resolver CUDA block 线程数，须为 32 的倍数且不超过设备上限，通常为 32–1024 |
| `tail_protected_pages` | `2` | 每请求保护的最新 FULL 页数 |
| `decode_emergency_reclaim` | `false` | 兼容旧配置；频次 Hand 不再区分普通与应急缩容权限 |

`top_k`、`swap_in_block_size` 和 `tail_protected_pages` 须为正整数，`logical_capacity_ratio` 须为不小于 1 的有限数，支持小数并向上对齐到整页；`logical_capacity_tokens` 须为非负整数，`host_ratio` 须为有限正数，应急开关须为布尔值；未知字段报错。`--kvduo-config` 必须配合 `--enable-kvduo`。旧 `max_relative_miss_increase` 字段已移除。

KVDuo 要求 RadixTree，不能与 HiSparse、HiCache 或 speculative decoding 同时启用；支持 chunked prefill，不改其分块设置。通用 DSA 和 DeepSeek-V4 均按实际存储层数计算 HOT 页容量；`flashmla_kv` 要求 FP8 KV 存储，BF16 使用受支持的其他稀疏 backend。

KVDuo 的 `--swa-full-tokens-ratio` 默认值为对应模型默认值的 1/2.5；DeepSeek-V4 为 `0.04`。非默认的显式配置保持不变。

`host_ratio` 覆盖主 KV、indexer、C128、SWA 和前缀恢复所需压缩状态的 Host 数据池；按设备历史池和 SWA 窗口池的页数乘倍率、向下取整，不包括控制元数据和临时搬运缓冲区。它不决定 HBM 分池或 logical 容量。KVDuo 以普通路径的物理缓存容量为目标，先确定独立的 logical 目标，再核算配套 indexer、映射和历史状态开销；DeepSeek-V4 的 SWA 按物理容量规划，不随 logical 超配扩大。`mem_fraction_static` 提供基础预算，KVDuo 允许额外使用运行余量中超过现有 activation、CUDA Graph 和 DeepEP 预留估计的部分；余量不足时降低物理容量，保持 logical 目标不变；目标的实际后备与至少一页物理存储都无法容纳时启动报错，不静默缩小 logical 或跳过预算检查。逻辑张量在启动时分配，运行中地址和形状保持固定；这不是无限地址或运行时动态扩容。扩大 logical 仍可能减少 FULL/HOT 空间，且不自动扩大 Host；准入继续检查各池实际容量。启动日志报告预算与容量，不能保证与普通路径容量完全相同。单请求所需主 KV 后备超过 Host 主池总容量时明确拒绝；仅因临时占用不足时等待。启动日志报告各 Host 池实际分配字节数。KVDuo 不再接受 `host_size` 或 `host_to_device_ratio`，旧命令需删除这些字段并改用 `host_ratio`；HiSparse 的配置保持不变。
